# Adobe docs split three Lightroom paths

As of 20 October 2026, the chat’s split between cloud services and Lightroom Classic holds in Adobe’s published documentation, and its ranked desktop-automation strategy does not. Cloud Lightroom still has no published Lua, UXP, CEP, or COM host: the cloud FAQ updated 27 August 2025 says Lightroom does not currently support third-party plug-ins, and the 16 September 2026 extensibility post leaves Lightroom outside the UXP rollout. The Catalog API at `https://lr.adobe.io` remains the documented cloud path for entitled partners, and `PUT /v2/catalogs/{catalog_id}/assets/{asset_id}/xmp/develop` still documents copying another asset’s external develop XMP. The Firefly Services Lightroom API’s published end of life is **31 July 2026**, with its five edit endpoints mapped to Photoshop API v2 `POST /v2/edit`, but that page was still written in the future tense on 20 October and does not appear on the Catalog changelog. Adobe for Creativity and Zapier’s Lightroom MCP publish image or file workflows, and neither documents catalog writes or desktop control. Of the eight proposed enhancements for a Classic Lua plug-in plus a Python MCP server, develop snapshots, HSL and color-grading sliders, and culling metadata are documented Classic SDK operations; adaptive AI masks and virtual-copy previews are only partly specified; a guaranteed second preview pass, an intent-based auto edit inside Classic, and a Windows UI worker for AI Denoise, Super Resolution, and HDR merge are not.

## Cloud Lightroom still publishes no plug-in host

The chat’s claim that cloud Lightroom has no Lua, UXP, CEP, or COM host holds as a statement about **published** interfaces, with a narrower proof than a blanket denial. Adobe’s cloud developer page, “Build applications that work with Lightroom,” describes streamlining workflows through RESTful endpoints and does not describe an in-process plug-in SDK, a UXP host, a CEP host, or a COM server ([Lightroom developer page](https://developer.adobe.com/lightroom/)). The Creative Cloud platform lists those REST services and Lightroom Classic as separate products, and the Classic landing page is the one that says plug-ins are built in Lua ([Creative Cloud developer platform](https://developer.adobe.com/creative-cloud); [Lightroom Classic](https://developer.adobe.com/lightroom-classic/)). The cloud FAQ, last updated 27 August 2025, answers that Lightroom does not currently support third-party plug-ins ([Lightroom common questions](https://helpx.adobe.com/lightroom-cc/faq.html)). The Classic Programmers Guide, copyright 2007–2022, pins that product’s scripting language at **Lua 5.1.4** and shows plug-ins as `.lrplugin` / `.lrdevplugin` folders ([SDK Programmers Guide](https://ioconsolerykerprodcdn.azureedge.net/static/installers/lr/sdk/2023/cross_platform/v5/doc/Lightroom%20Classic%20SDK%20Guide_1670563540.pdf)). The cloud FAQ does not itself name the `.lrplugin` extension, so “cloud Lightroom does not load Classic packages” is the combination of that FAQ with the Classic-only packaging docs.

The 2022 and 2026 extensibility posts do not close the host question as tightly as the chat implies. Adobe’s July 2022 Exchange FAQ says neither Lightroom nor Lightroom Classic had plans for CEP, and that neither had UXP on the roadmap “at the time of this writing” ([July 2022 developer blog](https://blog.developer.adobe.com/en/publish/2022/07/lightroom-classic-plugin-support-for-the-adobe-exchange-for-creative-cloud)). That sentence is explicitly time-bounded, and no later Adobe page found here renews or withdraws it. The 16 September 2026 post “Investing in the Future of Creative Cloud Extensibility” says the CEP-to-UXP transition “applies to Creative Cloud desktop flagship apps only; Acrobat, Adobe Express, and Lightroom aren’t affected,” lists UXP status only for Media Encoder, Premiere, After Effects, InDesign, Illustrator, and Photoshop, and gives Lightroom no UXP beta date ([September 2026 developer blog](https://blog.developer.adobe.com/en/publish/2026/09/investing-in-the-future-of-creative-cloud-extensibility-uxp-comes-to-our-flagship-applications)). “Aren’t affected” means that transition does not change the product Adobe calls Lightroom. It does not inventory a UXP host, a CEP host, a COM object, or an accessibility map, and the post does not say “Lightroom Classic,” so it does not settle Classic either. An October 2026 Developers Live recap summary covers the CEP-to-UXP roadmap, Express connectors, and agent plans, and the retrieved summary does not announce a Lightroom desktop plug-in host ([October 2026 recap](https://blog.developer.adobe.com/en/publish/2026/10/adobe-developers-live-2026-recap-cep-to-uxp-migration-express-connectors-and-what-we-publish-next)). No Adobe page found publishes a COM ProgID, type library, or Windows automation object for the cloud app. That is an absence after searching the developer portal and those posts, and it is evidence against a published COM host.

## The catalog API still copies external develop XMP

The chat’s claim that the Catalog REST API remains the cloud automation path, and that it can copy external XMP develop settings, holds for the surface Adobe actually specifies. The service base is **`https://lr.adobe.io`**, with `/v2/...` paths, an `X-API-Key`, and `Authorization: Bearer` ([Calling a Lightroom API](https://developer.adobe.com/lightroom/lightroom-api-docs/guides/calling-api/); [OpenAPI swagger.json](https://raw.githubusercontent.com/AdobeDocs/lightroom-public-apis/main/static/swagger.json)). The OpenAPI file on `main` at commit `e6d8ae8` (19 August 2026) lists **20 operations** under Health, Accounts, Catalogs, Assets, and Albums: health, account, catalog, create and read assets, upload a master (200 MB per call), generate and fetch renditions, generate and fetch a C2PA-signed JPEG export, put and get external XMP develop settings, and album create, read, update, delete, list, and asset membership ([swagger.json](https://raw.githubusercontent.com/AdobeDocs/lightroom-public-apis/main/static/swagger.json)). Access is an Adobe I/O Console integration that adds “Lightroom Services,” and tokens must include `openid`, `AdobeID`, `lr_partner_apis`, and `lr_partner_rendition_apis`. The prose still calls the caller an entitled partner. Refresh-token renewal, and on-demand `fullsize` and `2560` renditions, require contacting Adobe ([Authenticating Customers](https://developer.adobe.com/lightroom/lightroom-api-docs/getting-started/authenticate-customers/); [Read and Generate Renditions](https://developer.adobe.com/lightroom/lightroom-api-docs/getting-started/read-generate-renditions/)). `GET /v2/account` must show entitlement `subscriber` or `trial`, or other calls return 403 ([Upload Customer Images and Videos](https://developer.adobe.com/lightroom/lightroom-api-docs/getting-started/upload-content/)).

Copying develop settings is real, and it is one content type on one path. Changelog Version 1.1.0 (3 February 2021) added `PUT` and `GET` `/v2/catalogs/{catalog_id}/assets/{asset_id}/xmp/develop` as upload and read of an external XMP develop file ([API Change Logs](https://developer.adobe.com/lightroom/lightroom-api-docs/release-notes/)). The current OpenAPI description of `putAssetExternalXmpDevelopSetting` says the same call supports two workflows: `Content-Type: application/rdf+xml` uploads the file, and `Content-Type: application/json` with `file_href` set to another asset’s `/xmp/develop` link copies that asset’s external XMP ([swagger.json](https://raw.githubusercontent.com/AdobeDocs/lightroom-public-apis/main/static/swagger.json)). There is no second path named “copy develop settings.” The 2021 changelog text does not mention the JSON copy mode; that wording is in the spec as of 19 August 2026, and the date it was added was not established. The RDF body is described in prose, the OpenAPI content map declares only the JSON copy body, and no schema lists which `crs:` fields, masks, or AI edits the document may contain. A string search of that OpenAPI file finds zero hits for `keyword`, `mask`, `slider`, `lrcat`, and `Firefly`. `rating` appears only as the sort values `ratingAsc` and `ratingDesc`. Create-asset metadata is capture date plus import source. The `develop` object in the asset response example is an example payload, and it is absent from the create-asset request schema. Album update and delete are limited to albums this client created with subtype `project` or `project_set`.

The published changelog’s last versioned capability entry is still **Version 1.2.1 (18 May 2021)**. The docs repository has later edits the changelog page does not record, including the 19 August 2026 reapplication of export operations that optionally embed a signed C2PA manifest on JPEG output at long-edge 2048, 4096, or fullsize ([commit e6d8ae8](https://github.com/AdobeDocs/lightroom-public-apis/commit/e6d8ae8); [API Change Logs](https://developer.adobe.com/lightroom/lightroom-api-docs/release-notes/)). A direct GET of the developer-portal `swagger.json` returned HTTP 404 on 20 October, so it is unverified whether production has deployed that commit. 2026 catalog-doc changes that were read are documentation of existing 403 entitlement strings (`UnexpectedEntitlementError`, `EntitlementExpiredError`) and of empty-body HTTP 429 after a “CGW migration,” plus the export addition ([PR 79](https://github.com/AdobeDocs/lightroom-public-apis/pull/79); [PR 77](https://github.com/AdobeDocs/lightroom-public-apis/pull/77)). The Catalog FAQ source is still the placeholder “Lorem ipsum,” so Adobe has not published a limitations blacklist that names desktop UI, local `.lrcat` files, or newer AI edits ([FAQ source](https://raw.githubusercontent.com/AdobeDocs/lightroom-public-apis/main/src/pages/support/FAQ/index.md)). Those capabilities sit outside the specified resources. Developer guidelines warn that undocumented behavior can stop without notice ([Developer Guidelines](https://developer.adobe.com/lightroom/lightroom-api-docs/getting-started/developer-guidelines/)).

## Imaging connectors stay outside catalog and desktop control

The chat’s claim that the Firefly Lightroom imaging API ended on 31 July 2026 and moved to Photoshop API v2 matches Adobe’s migration schedule for five edit routes, and it does not describe a confirmed outage or a move of the Catalog API. The Firefly Services deprecation page says the Lightroom API “will reach end-of-life (EoL) on July 31, 2026” and tells customers to migrate to Photoshop API v2 before August 2026, because Adobe is consolidating imaging capabilities into that API ([Deprecation announcement](https://developer.adobe.com/firefly-services/docs/lightroom/getting-started/deprecation-announcement/)). The same date is the published end of life for Photoshop API v1 ([Photoshop API overview](https://developer.adobe.com/firefly-services/docs/photoshop/)). Fetched on 20 October 2026, after that date, the deprecation page still uses “will reach” and “before August of 2026.” These notes do not establish whether `image.adobe.io` Lightroom routes have actually stopped. The Catalog changelog, overview, and OpenAPI file do not contain that end-of-life sentence ([API Change Logs](https://developer.adobe.com/lightroom/lightroom-api-docs/release-notes/); [Firefly Services Lightroom overview](https://developer.adobe.com/firefly-services/docs/lightroom/)).

The published mapping sends `/lrService/autoTone`, `/lrService/autoStraighten`, `/lrService/presets`, `/lrService/xmp`, and `/lrService/edit` to **`POST /v2/edit`** on `https://photoshop-api.adobe.io`, and `/lrService/status/{jobId}` to `/v2/status/{jobId}` ([Migration to v2 overview](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/)). The v2 auto-tone example posts `image.source.url` as a signed GET URL and `outputs[].destination.url` as a signed POST URL, with `edits.autoTone: true` ([Edit operations migration](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/edit-operations)). Authentication stays OAuth server-to-server client credentials (`grant_type=client_credentials`, scope `openid,AdobeID,read_organizations`), which is a developer-project token, and the documented Lightroom user scopes of the Catalog API are a different contract ([LLM migration reference](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/llm-migration-reference)). The still-published v1 Apply Edits guide describes `/lrService/edit` as programmatic control of the same adjustments as the Lightroom Edit panel, against signed URLs, with no catalog id, album id, or desktop command ([Apply Lightroom API edits](https://developer.adobe.com/firefly-services/docs/lightroom/guides/apply-edits/)). Adobe’s own pages then contradict a blanket “everything moved.” The behavior catalog says all `/lrService/*` calls go to `/v2/edit`. The Edit Operations page lists `/lrService/mask` as removed as a standalone endpoint with mask functionality now through XMP on `/v2/edit`, `/lrService/predict` as removed, `/lrService/depthRefinement` as no longer supported, `/lrService/index` as having no v2 equivalent, and `/lrService/xmpToPreset` as planned for a future release ([V2 API behavior catalog](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/v2-api-catalog); [Edit operations migration](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/edit-operations)). A second contradiction: the LLM reference says v1 `/lrService/mask` is a separate AI mask feature (selectSubject, selectSky) with a different deprecation path from XMP mask files ([LLM migration reference](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/llm-migration-reference)). No Lightroom row in those tables is named convert. Format conversion is Photoshop’s `/pie/psdService/renditionCreate` moving to `/v2/create-composite`. `lightroomPath` appears only as one allowed artboard image source beside `url`, `creativeCloudPath`, and `creativeCloudFileId`, and the page does not define what that string addresses ([LLM migration reference](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/llm-migration-reference)).

Adobe for Creativity and Zapier do not, on the pages fetched, replace desktop or catalog control. Adobe’s plugin manifest sets a single HTTP MCP server at **`https://adobe-creativity.adobe.io/mcp`** and lists no tools ([adobe/skills `.mcp.json`](https://raw.githubusercontent.com/adobe/skills/main/plugins/creative-cloud/adobe-for-creativity/.mcp.json)). The product page says the connector offers 50+ tools across Photoshop, Lightroom, Illustrator, Firefly, Premiere, Express, InDesign, and Adobe Stock, inside Claude chat, Cowork, and Claude Desktop, with guests getting about 40 tools ([Adobe for Creativity](https://developer.adobe.com/adobe-for-creativity/)). Adobe publishes skill names, including `adobe-batch-edit-photos` and `adobe-retouch-portraits` (“auto-straighten, auto-tone, and auto-light across a folder”), and describes inputs as headshots, a set of images, or a folder, with handoff by download, Firefly Boards, or Express ([adobe/skills README](https://github.com/adobe/skills/); [Prompts and workflows](https://developer.adobe.com/adobe-for-creativity/prompts-and-workflows/)). No fetched Adobe page names an MCP tool whose input is a Lightroom catalog, album, or the installed desktop app, and Adobe did not publish a `tools/list` payload here. Absence of a catalog tool is undocumented scope, and it is enough to say these pages do not document a replacement for catalog or desktop control. Zapier’s Lightroom MCP page, fetched the same day, advertises five file actions: Apply AutoTone, Apply Presets, Convert File, and two job-status checks, with inputs of file storage, file location, presets files, output type, and job id, served from `mcp.zapier.com` ([Zapier Adobe Photoshop Lightroom MCP](https://zapier.com/mcp/adobe-photoshop-lightroom)). Neither that page nor Adobe’s deprecation and v2 pages say which Adobe backend those actions call, or whether they still run after 31 July 2026. The action list is files in and files out. The community project Automaat/lightroom-mcp is the one product in these notes whose own README says it talks to a Lightroom catalog, and the product it names is Classic, through Plug-in Manager, on macOS or Windows ([Automaat/lightroom-mcp](https://github.com/Automaat/lightroom-mcp)).

## Classic SDK backs color, snapshots, and culling metadata

Judgments below come from the 2007–2022 Programmers Guide and from `https://lrc.mcor.dev/`, a third-party HTML mirror whose newest “first supported” stamps found here are **SDK 14.3**. Adobe help navigation already names Classic 15.3, in a troubleshooting link titled “Denoise is not working in Lightroom Classic version 15.3 and earlier,” on a comparison page last updated 20 February 2026 ([Feature comparison](https://helpx.adobe.com/lightroom-classic/kb/lightroom-feature-comparison.html)). The official API reference inside the current SDK zip was not opened. “Documents support” means the symbol appeared on a page that was opened. Silence means it was not found there, and a newer console-only SDK could contain calls this mirror lacks. Develop-settings APIs carry Adobe’s own experimental warning: do not depend on the settings table remaining compatible, and the definitive list is the one shown in the UI ([LrPhoto](https://lrc.mcor.dev/modules/LrPhoto.html)).

**Intent-based auto edit** is a Photoshop API v2 file operation, and it is absent from the Classic pages opened. `POST /v2/edit` with `edits.autoTone: true` adjusts an image the caller supplies by URL and writes an output URL ([Edit operations migration](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/edit-operations)). Zapier’s Apply AutoTone action is the same shape of file in, file out, with the backend unstated ([Zapier Adobe Photoshop Lightroom MCP](https://zapier.com/mcp/adobe-photoshop-lightroom)). The Catalog API has no auto-tone operation. Classic documents `LrDevelopController.setValue` and `getValue` for named parameters on the current photo while the Develop module is active, first supported in SDK 6.0, and `photo:applyDevelopSettings` for a settings table with an optional history-step name ([LrDevelopController](https://lrc.mcor.dev/modules/LrDevelopController.html); [LrPhoto](https://lrc.mcor.dev/modules/LrPhoto.html)). Those calls set sliders the plug-in already chose. They are not an intent or auto-tone method.

**A second preview pass** is not what `photo:requestJpegThumbnail` documents. The method, first supported in SDK 5.0, requests JPEG bytes and renders when the preview system does not already contain a preview at the requested size. Sizes are minimums, the call must run inside an `LrTasks` async task, and the caller must hold the request object until the callback ([LrPhoto](https://lrc.mcor.dev/modules/LrPhoto.html)). The documented trigger is a cache-size miss. A cached preview of an older state satisfies the wording, so the call is not a guaranteed frame of a develop change that was just written, and the page does not describe a second vision pass. The Programmers Guide says export rendition requests are finally passed to Classic’s built-in rendering engine, which is a separate export workflow; the `LrExportSession` and `LrExportRendition` method pages were not opened ([SDK Programmers Guide](https://ioconsolerykerprodcdn.azureedge.net/static/installers/lr/sdk/2023/cross_platform/v5/doc/Lightroom%20Classic%20SDK%20Guide_1670563540.pdf)). On the cloud side, the rendition guide says that after an edit, `thumbnail2x`, `640`, `1280`, and `2048` are recreated with edits applied, while `fullsize` and `2560` are on-demand and deleted after one day, and generative-AI Content Credentials in that print workflow are available only for fullsize ([Read and Generate Renditions](https://developer.adobe.com/lightroom/lightroom-api-docs/getting-started/read-generate-renditions/)). That is a cloud rendition rule, and it is a different product from a Classic plug-in preview.

**Snapshots and undo** are the clearest supported enhancement, with undo narrower than the History panel. `photo:createDevelopSnapshot`, `getDevelopSnapshots`, `applyDevelopSnapshot`, and `deleteDevelopSnapshot` create, list, restore, and delete named snapshots. Create must run inside `catalog:withWriteAccessDo` or `withProlongedWriteAccessDo`. List entries contain `snapshotID`, `name`, and `id_global` ([LrPhoto](https://lrc.mcor.dev/modules/LrPhoto.html)). `applyDevelopSettings` can name the history step. `LrDevelopController.startTracking` and `stopTracking` group parameter changes into a single history state. `LrUndo.undo` and `LrUndo.redo` undo and redo **the last history state** only, first supported in SDK 6.0 ([LrUndo](https://lrc.mcor.dev/modules/LrUndo.html); [LrDevelopController](https://lrc.mcor.dev/modules/LrDevelopController.html)). No symbol found returns the history-step list or restores a chosen older step. Help describes both snapshots and the History panel as Develop UI, where selecting a state reapplies it or saves it as a snapshot ([Develop module options](https://helpx.adobe.com/lightroom-classic/desktop/process-and-develop-photos/develop-module-options.html)). The SDK snapshot calls are on `LrPhoto` and do not say the Develop module must be active.

**Adaptive AI masks** are partly specified. `LrDevelopController.createNewMask(maskType, maskSubtype)`, first supported in SDK 11.0, must run while Develop is active. `maskType` includes `"aiSelection"`, and the subtype list for that type includes `"subject"`, `"sky"`, `"background"`, `"objects"`, `"people"`, and `"landscape"`, plus `"color"`, `"luminance"`, and `"depth"` ([LrDevelopController](https://lrc.mcor.dev/modules/LrDevelopController.html)). The same subtypes are documented for add, intersect, and subtract. The page does not say the call blocks until the mask is computed, and it does not apply local adjustments in that call. `photo:applyDevelopPreset` takes an optional `updateAISettings` boolean, default false, described as whether AI settings should be auto-updated after the preset. `photo:updateAISettings`, first supported in SDK 13.3, “updates AI settings” and does not define which features that includes ([LrPhoto](https://lrc.mcor.dev/modules/LrPhoto.html)). The docs do not say that flag recomputes Select Subject, Sky, or Background. Help and the February 2026 feature comparison use the product name “Adaptive Presets” and describe applying an AI mask from User Presets or the Adaptive Presets for Subject, Sky, and Portrait as Develop panel actions ([Masking tool](https://helpx.adobe.com/lightroom-classic/desktop/process-and-develop-photos/masking.html); [Feature comparison](https://helpx.adobe.com/lightroom-classic/kb/lightroom-feature-comparison.html)). That phrase was not found on the SDK pages opened. `LrDevelopPreset` methods on the page opened are `getFile`, `getName`, `getParent`, `getSetting`, `getUuid`, and `type`. `getFile` returns the path of a preset Classic already has. `LrApplication.addDevelopPresetForPlugin` takes a Lua settings table, not a file path. Loading an arbitrary user `.xmp` that is not already a preset was not found. `getDevelopSettings` lists `MaskGroupBasedCorrections` as a table from SDK 11.0 and does not document its fields, so a round-trip of an AI mask through `applyDevelopSettings` is unspecified there. The Catalog OpenAPI file has no `mask` path.

**HSL and color grading** are documented slider names on the Develop controller. The `mixerPanel` list covers hue, saturation, and luminance adjustments for Red, Orange, Yellow, Green, Aqua, Blue, Purple, and Magenta. The `colorGradingPanel` list includes `SplitToningShadowHue`, `SplitToningShadowSaturation`, `ColorGradeShadowLum`, `SplitToningHighlightHue`, `SplitToningHighlightSaturation`, `ColorGradeHighlightLum`, `ColorGradeMidtoneHue`, `ColorGradeMidtoneSat`, `ColorGradeMidtoneLum`, `ColorGradeGlobalHue`, `ColorGradeGlobalSat`, `ColorGradeGlobalLum`, `SplitToningBalance`, and `ColorGradeBlending` ([LrDevelopController](https://lrc.mcor.dev/modules/LrDevelopController.html)). `setValue` and `getValue` accept any name in that list, for the current photo, with Develop active. The enumerated `photo:getDevelopSettings()` members include the HSL names and the `SplitToning*` names, plus SDK 4.0 process-version names such as `Exposure2012` and `Highlights2012`, and they do not include the `ColorGrade*` names. `LrDevelopPreset:getSetting` uses a different plural style (`HueAdjustmentReds`) and also omits `ColorGradeMidtoneHue`. Writing the color-grade strings is therefore documented through the controller. Reading them back from the settings table is not shown for the `ColorGrade*` keys, and whether `applyDevelopSettings` accepts those keys is unstated. Exposure, Contrast, Highlights, and Shadows are in the same controller list. The Catalog API has no slider resource. Photoshop API v2’s edit group can combine `light`, `color`, `detail`, `effects`, `optics`, and XMP presets on a file, which is the imaging-service analogue and writes an output file ([V2 API behavior catalog](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/v2-api-catalog)).

**Virtual-copy preview** is supported up to the point of creating a separate photo object and asking it for a thumbnail. `LrPhoto` “represents a single photo or virtual copy.” `catalog:createVirtualCopies(copyName)`, first supported in SDK 5.0, creates a copy for each selected photo, returns an array of `LrPhoto`, and then selects the new copies ([LrCatalog](https://lrc.mcor.dev/modules/LrCatalog.html)). `applyDevelopSettings` targets the `LrPhoto` it is called on, so the documented way to edit the copy is to call it on a returned object rather than on `masterPhoto`. `getRawMetadata` exposes `isVirtualCopy`, `masterPhoto`, `virtualCopies`, and `countVirtualCopies`. Because a virtual copy is an `LrPhoto`, `requestJpegThumbnail` is available on it, and the cache-size wording still applies: the docs do not promise a freshly rendered view of the copy’s new settings. No sentence found says the master is left unchanged, or that a virtual copy’s preview is stored apart from the master’s. The February 2026 feature comparison lists Classic copies as “Virtual” and ecosystem copies as “Duplicate” ([Feature comparison](https://helpx.adobe.com/lightroom-classic/kb/lightroom-feature-comparison.html)). The Catalog API has no virtual-copy operation.

**Burst-culling metadata** is documented as ordinary photo metadata, and burst detection itself is not an SDK method. `photo:setRawMetadata`, inside a write-access gate, accepts `rating` (nil or a number of stars), `title`, `caption`, and, from SDK 4.0, `pickStatus` with 1 for picked, 0 for not set, and −1 for rejected ([LrPhoto](https://lrc.mcor.dev/modules/LrPhoto.html)). `LrSelection.setRating` takes 0 through 5, and `flagAsPick`, `flagAsReject`, and `removeFlag` set the flag for the grid selection or, outside grid view, the active photo ([LrSelection](https://lrc.mcor.dev/modules/LrSelection.html)). Keywords are `LrKeyword` objects: `catalog:createKeyword` takes a name, synonyms, an export flag, and a parent, and `photo:addKeyword` / `removeKeyword` take that object, so hierarchy is the `parent` argument rather than a string path written in one call ([LrCatalog](https://lrc.mcor.dev/modules/LrCatalog.html)). The Catalog API documents none of these writes.

**A Windows UI worker for AI Denoise, Super Resolution, and HDR merge** is not supported by the SDK pages opened, and the chat’s fallback order does not turn the gap into a measured design. Searches of `LrDevelopController` for Denoise, Super Resolution, Enhance, Photo Merge, and `setEnhance` found no matches. `getDevelopSettings` lists `HDREditMode`, `HDRMaxValue`, and `SDRBrightness`, `SDRContrast`, `SDRClarity`, `SDRHighlights`, `SDRShadows`, `SDRWhites`, and `SDRBlend` from SDK 13.0, which are HDR edit and output fields on a photo, and the page does not describe merging a bracket ([LrPhoto](https://lrc.mcor.dev/modules/LrPhoto.html); [LrDevelopController](https://lrc.mcor.dev/modules/LrDevelopController.html)). Help, last updated 1 May 2026, places Denoise, Raw Details, and Super Resolution in the Detail panel, says they run in the background, and says an image can be enhanced only once, with no Lua symbol on the page ([Classic Enhance](https://helpx.adobe.com/lightroom-classic/desktop/process-and-develop-photos/enhance-details.html)). HDR merge help says Photo > Photo Merge > HDR, or Ctrl+H, then a preview dialog and a Merge button ([HDR photo merge](https://helpx.adobe.com/lightroom-classic/help/hdr-photo-merge.html)). The SDK documents adding the plug-in’s own items under Plug-in Extras, with a Windows accelerator on that new item, and it documents fixed commands such as `LrSelection.flagAsPick` and `LrDevelopController.goToMasking` ([SDK Programmers Guide](https://ioconsolerykerprodcdn.azureedge.net/static/installers/lr/sdk/2023/cross_platform/v5/doc/Lightroom%20Classic%20SDK%20Guide_1670563540.pdf); [LrSelection](https://lrc.mcor.dev/modules/LrSelection.html)). No `LrMenu` namespace and no function that takes a menu path or shortcut string were found. Because the mirror’s highest stamp found is 14.3, a 15.x SDK could have added Enhance calls that were not seen. Third-party notes that mention `setEnhance` or `EnableAIDenoise` were not on the controller page opened and are not treated as the SDK ([lightroom-ai-bridge command reference](https://github.com/aslanoov/lightroom-ai-bridge/blob/main/docs/COMMAND-REFERENCE.md)).

The proposed desktop order — UI Automation, then keyboard, then computer vision, and never fixed coordinates — is a general Windows habit, and nobody has published a Lightroom result for it. No 2024–2026 Inspect.exe or Accessibility Insights tree for cloud Lightroom on Windows was found. The newest cloud Windows accessibility conformance report in a third-party Adobe index is still **Adobe Lightroom Windows v2.4.1, November 2019** ([ACR Index](https://acrindex.com/adobe/); [Lightroom Windows v2.4.1 ACR](https://www.adobe.com/trust/accessibility/conformance/adobe-lightroom-win-2019-acr.html)). That report’s criterion 4.1.2 Name, Role, Value is “Does Not Support,” with icon buttons and slider controls given as examples that lack programmatic name, role, or state, and criterion 2.1.1 Keyboard is “Does Not Support,” with most controls not receiving keyboard focus. It is seven years and many versions before 20 October 2026, it publishes no element tree, and it does not make a UIA-first design known to be viable. Classic’s separate August 2023 report likewise publishes no tree ([Lightroom Classic Windows ACR](https://www.adobe.com/trust/accessibility/conformance/adobe-lightroom-classic-win-acr.html)). Adobe has not named the cloud app’s UI toolkit. A 2026 Wine port of Lightroom CC 9.3.1 records that the main window asks Direct2D for a color-management effect, and that the process static-imports `UiaDisconnectAllProviders`; the same notes’ WebView2/Electron remark is tied to the Creative Cloud sign-in shell, not to a dumped edit-panel tree ([lightroom-cc-on-linux GUIDE](https://github.com/sander110419/lightroom-cc-on-linux/blob/main/GUIDE.md)). A static UIA import does not show which controls are published.

Keyboard is similarly thin. Cloud Help, last updated 17 June 2025, assigns Windows **Ctrl+Alt+E** both to batch-apply Denoise and to opening the Enhance dialog, while the desktop shortcut catalog extract does not list Denoise, Enhance, or that chord ([Enhance in Lightroom](https://helpx.adobe.com/lightroom/desktop/edit-photos/enhance-details.html); [Lightroom desktop shortcuts](https://helpx.adobe.com/lightroom/desktop/using/keyboard-shortcuts.html)). The same article says Denoise now lives in the Detail panel “instead of creating separate files” and also says the result is saved as a new `Enhance-NR.dng`. Classic’s shortcut page, with a search extract dated 29 October 2025, documents Ctrl+Alt+I to open Enhance, Ctrl+Alt+Shift+I for headless enhance, and Ctrl+Alt+E as “Open in other editor” ([Lightroom Classic shortcuts](https://helpx.adobe.com/lightroom-classic/desktop/introduction-to-lightroom-classic/keyboard-shortcuts.html)). No HelpX shortcut is named “AI Denoise.” OpenCV template matching and any ban on fixed coordinates are unpublished for this app. The tooling around UIA is also a weak foundation for a new worker: WinAppDriver’s latest GitHub release is still the July 2021 pre-release **v1.2.99**, and Microsoft’s 2021 FAQ, still open, says resourcing was paused with no timeframe ([WinAppDriver v1.2.99](https://github.com/microsoft/WinAppDriver/releases/tag/v1.2.99); [issue #1550](https://github.com/microsoft/WinAppDriver/issues/1550)). Appium Windows Driver **6.3.1**, published 8 October 2026, still describes itself as a proxy to WinAppDriver ([appium-windows-driver 6.3.1](https://www.npmjs.com/package/appium-windows-driver)). FlaUI’s latest GitHub release is v5.0.0 from 25 February 2025, with later commits on `main` and no newer tag found ([FlaUI v5.0.0](https://github.com/FlaUI/FlaUI/releases/tag/v5.0.0)). Microsoft documents that `SendInput` fails silently under UIPI when the target is higher integrity, that `SetForegroundWindow` cannot steal focus while the user is in another window, and that a locked desktop, the logon UI, and a UAC consent UI are outside normal cross-process input ([SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput); [SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow); [UI Automation security](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-securityoverview)).

## Conclusion

The useful change is to stop treating “Lightroom API” as one migrating product with a desktop fallback underneath it. A partner who can obtain `lr_partner_apis` still has a live cloud catalog, including an XMP copy and, in the August 2026 spec, a signed JPEG export. A Firefly imaging caller was told to retarget five edit routes at Photoshop API v2 and to expect a file URL back. A Classic plug-in can name sliders, snapshots, and culling fields, and it cannot, on the reference opened here, ask Classic to run Enhance or Photo Merge.

For the MCP server, that means shipping the enhancements whose symbols already exist, and treating Denoise, Super Resolution, and HDR merge as blocked on a newer SDK reference than the 14.3 mirror. Inventing a Windows UI worker would add a control channel Adobe has not published. The last accessibility inspection Adobe did publish already failed name, role, value, and keyboard access, and no 2024–2026 tree has replaced it. Until that tree or a documented Enhance symbol exists, those three commands stay outside the server.
